# nblaunch Open Questions and Risks

## Current Assumptions
- Notebook launch links are generated by a trusted upstream that shares `NBLAUNCH_HMAC_SECRET` with nblaunch.
- JupyterHub is the source of truth for authenticated user identity and per-user home-subpath metadata.
- nblaunch may write notebooks only inside the configured notebook base directory and validated Hub-provided user subpath.
- `/oauth_callback` behavior is tied to JupyterHub service OAuth, not a standalone auth system.

## Open Questions
- What is the stable Hub-side implementation and ownership model for the `/services/nblaunch/home-subpath/<username>` endpoint?
- What notebook filename policy should apply on collisions: overwrite, suffix, or reject?
- Are the current timeout and size defaults correct for production workloads?
- What structured logging and audit fields are required for launch attempts?
- Should the service eventually expose readiness details beyond the current simple `/healthz` response?

## Risks To Validate In Real Deployments
- Clock skew between the link generator and nblaunch can raise `401` rates if TTL is too strict.
- Hub API schema or authorization drift can break home-subpath resolution.
- Large notebook downloads can create memory or latency pressure.
- Filesystem permission mismatches can cause persistent write failures.
- Over-broad service token scope should be validated during Hub integration.
- Redirect construction bugs remain security-sensitive and should stay covered by tests.
